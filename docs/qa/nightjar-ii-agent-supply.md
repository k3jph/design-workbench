# Nightjar II: agent archive supply-chain evidence

Baseline: the frozen Nightjar I integration candidate `5138a89fc2956d9019d5bd720c987b8b9e24533b`. This record concerns the generator and locally generated artifacts; it does not claim to update the published reference archive, tracked host Workers, live sites, or existing downloads.

## Reproduction and correction

The root workbench lock was already on Zod 4.6.7, but `mcp/agent-lock.json` and the independently generated agent package manifest pinned 4.3.6. Building the candidate and running `npm audit --package-lock-only` within the generated Martlet agent directory on 30 October 2026 reported one high finding: GHSA-mrhx-c7xc-m3w5, affecting Zod versions below 4.6.6. The same lock was used for both families. This finding identifies an affected dependency; it does not establish that a malicious input can reach the vulnerable SDK validation path or compromise a deployed service.

The agent lock now pins 4.6.7, the same version as the root lock. The generated manifest takes its dependencies from the lock's root package rather than a second hard-coded list. Both generated packages are unpacked and installed with `npm ci --ignore-scripts` in independent temporary directories; each MCP server identifies its correct family and reports 61 references. A fresh `npm audit --package-lock-only --audit-level=low` inside each generated package reported zero findings at this snapshot. `npm audit` is advisory-database evidence, not a security certification.

## Worker initialization response amplification

An additional bounded local test exercised the actual tracked site Worker, not a hypothetical schema: a 20,160-byte JSON-RPC `initialize` request with 10,000 invalid `clientInfo.icons` entries produced a 2,078,977-byte SSE error in each family's existing Worker. The Zod 4.6.7 historical rebuild still produced a roughly 2.42 MB error, so the dependency upgrade alone does not prevent this behavior. The SDK validates initialization metadata and accumulates per-element issues before dispatch; this is an observed local response-amplification path within the configured 32,768-byte HTTP body cap, not evidence of an observed production outage or successful denial of service.

The workbench HTTP adapter now previews eligible JSON requests with a bounded stream reader before passing them to the SDK. It rejects aggregate initialization metadata above 128 icon entries or 256 icon-size entries with a compact HTTP 400 JSON-RPC invalid-request response. These are application limits, not MCP-wide limits. The limit is scoped to initialization icon metadata, sums entries across a batch and keeps the SDK's separate 32,768-byte body limit. Invalid short requests still reach the SDK and are rejected; other validation and stdout MCP behavior are unchanged. Tests cover both families, legacy and current-protocol clients, 10,000 bad icons or icon sizes, aggregate batches, CORS and JSON-RPC error shape, a valid initialization with 120 icons and 240 sizes plus an 18 KB description, and a streamed 32,769-byte body. Local patched Worker builds returned 119 bytes for the original adversarial request. The existing published Workers do not receive this guard until a separately reviewed and authorized artifact update; this guard does not claim to bound every possible SDK error path or establish platform-level resource safety.

## Artifact repeatability

The previously studied historical generator `7301241` did not normalize tar metadata and produced different tarball hashes across repeated builds. The frozen candidate had already added normalized tar ordering, timestamps, owners and modes and a reproducible ZIP writer: two candidate builds with `DESIGN_SOURCE_COMMIT=5138a89fc2956d9019d5bd720c987b8b9e24533b` produced identical SHA-256 hashes for both agent tarballs and both builder ZIPs in this Linux environment. This closes the previously reported *local* repeat-build gap for the candidate; it does not prove byte identity on other tar, gzip, Python or OS versions.

`npm run test:agents` now rebuilds twice, crossing a timestamp boundary, and compares SHA-256 hashes for all four archives before running the existing extracted-consumer checks. A deliberate isolated mutation removing tar normalization made the reproducibility assertion fail; the mutation was reverted and the unchanged test then passed. No golden images or archived payloads were approved or committed. Further cross-platform toolchain reproducibility and artifact-provenance verification remain open.

## Downstream and approval gates

Both source sites use `scripts/fetch-react-reference.mjs` to fetch a checksum-pinned reference archive and copy its agent artifacts during their build. Updating the workbench generator or a tracked site-side copy alone does not replace that published reference. The sites also have separate checked-in, prebundled Workers: an independent rebuild tied their current code to a source lock with Zod 4.3.6; SDK input reachability is not established. The source-site Astro/Node security draft PRs must not be described as complete remediation of either artifact. New Workers and generated reference archives require an independently reviewed provenance and release/adoption plan, and any publication, live repoint, production control change or deployment requires separate authorization. The generator fix here does not itself carry out those actions. Generated agent packages require Node `>=24.19.0 <25`, distinct from the source-site Node 22.19 build floor.

GitHub reported 65 default-branch workbench Dependabot alerts (4 critical, 25 high, 24 moderate, 12 low), but the available GitHub connector rejects the Dependabot API endpoint and the environment's enforced network policy blocks direct `api.github.com`. No alert has been dismissed. A repository security administrator with alert-read permission can open the repository's Security → Dependabot alerts page, or from an authorized network run `gh api --paginate 'repos/k3jph/design-workbench/dependabot/alerts?state=open&per_page=100'`. Record alert number, GHSA, severity, package, manifest, affected version, state, remediation and production/build reachability; reconcile the records with current locks, historical fixtures, Workers and downloaded archives, prioritizing critical then high.
