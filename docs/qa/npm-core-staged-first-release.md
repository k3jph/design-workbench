# First npm core publication: staged bootstrap proposal

**Preparation only.** Nothing in this document authorizes staging, publication, GitHub release, merge, trusted-publisher or environment changes, deployment, or deprecation. The real core packages and the bootstrap templates remain private in their source worktrees. The two `/theme` packages, their npm settings, and their historical tags are untouched.

## What npm actually does

npm supports creating a new package using `npm stage publish`. For a package that does not yet exist, the operation immediately creates a **public `0.0.0-stage` placeholder** and places the submitted version in a private staged queue. A staged version occupies the same version namespace as published versions; it is not safe to submit the intended release version as a disposable bootstrap. npm CLI 11.15.0+ and Node 22.14.0+ are required. Staging itself does not require a 2FA prompt; approval and rejection require 2FA. A staged package's distribution tag cannot be changed: reject and restage to change it. See [npm staged publishing](https://docs.npmjs.com/staged-publishing/) and [npm stage CLI](https://docs.npmjs.com/cli/v11/commands/npm-stage/).

A maintainer can create a new package via staged publishing using a local npm session or a granular access token, including a stage-only token; once created, package settings and trusted publishing can be configured. See [npm's package-creation announcement](https://github.blog/changelog/2026-10-02-npm-staged-publishing-now-supports-creating-new-packages/). Do not infer scope ownership or package availability from a 404. Have an npm owner verify the scopes, permissions, package existence, stage queue, 2FA and approved version/tag first.

## Separately authorized bootstrap and release sequence

1. **Review, do not run yet.** Approve or reject the public placeholder consequence, the bootstrap method and the proposed first versions separately. The inert templates in `fixtures/core-release/bootstrap/` use `0.0.0-bootstrap.0`, not either release version, are `private: true`, and contain no design-system implementation. Their sentinel is intended never to be approved or installed as a usable design language. Confirm the bootstrap version is unused. The bootstrap's `private` guard must be removed only in a separately approved disposable copy; do not alter the core source guard.
2. **Only after explicit bootstrap authorization**, a scope owner uses a trusted workstation/session with Node 22.14+ and npm 11.15+ to stage each reviewed disposable bootstrap copy using an explicit, nondefault tag, e.g. `npm stage publish /absolute/path/to/reviewed-bootstrap --access public --tag bootstrap`. Verify the directory's `name`, `version`, and `private:false` immediately before running it. This one action is a registry mutation, creates the public placeholder, and reserves the sentinel version. Record the stage ID. Do **not** approve the sentinel. If an identity already exists unexpectedly, stop rather than stage or alter ownership. Keep the sentinel pending while configuring trust; no assumption is made about placeholder lifetime if its only staged item is rejected.
3. **Only after separate trusted-publisher/environment authorization**, the maintainer opens each new package on npmjs.com → package settings → Trusted publishing and adds a GitHub Actions publisher. Enter these case-sensitive values:

   | npm package | Organization/user | Repository | Workflow filename | Environment |
   | --- | --- | --- | --- | --- |
   | `@martlet/core` | `martletdesign` | `core` | `core-stage.yml` | `core-stage-review` |
   | `@krigsvold/core` | `krigsvolddesign` | `core` | `core-stage.yml` | `core-stage-review` |

   Select stage-only: do not grant direct `npm publish` or dist-tag management. npm's stage permission and direct-publish permission are distinct. Each package can have multiple independent trusted publishers; inspect all existing configurations rather than assume one binding is exclusive. The workflow file must be present on the approved default branch. A named GitHub environment in YAML does **not** configure protection: an authorized repository administrator must separately create/verify `core-stage-review`, required reviewers and branch restrictions, then test that the desired protection is supported by the organization plan. Do not configure the new publishers far ahead of release: an unvalidated configuration expires after two days. npm does not validate the configuration when it is saved. See [npm trusted publisher configuration](https://docs.npmjs.com/trusted-publishers/).
4. The separate draft workflow PRs [Martlet #11](https://github.com/martletdesign/core/pull/11) and [Krigsvold #12](https://github.com/krigsvolddesign/core/pull/12) are deliberately inert (`if: false`) and manual-only. The current `publish.yml` remains a separate, release-triggered **direct publish** path. Review and separately authorize any merge, activation of the draft guard, environment protection, and the treatment of that direct-publish path before creating a GitHub Release. Do not assume the new disabled workflow gates the old workflow; do not change either legacy `/theme` publisher binding.
5. Rebuild and validate the exact publishable-form tarballs from the approved source and toolchain; supply the reviewed source SHA and SHA-256 to the separately activated workflow. The draft workflow verifies the repository, immutable SHA, `main` event revision and ancestry from `main`, package name/version and private source guard, builds/tests, derives an isolated manifest with `private:false`, and refuses to stage if the SHA-256 differs. GitHub environment approval is the proposed **pre-stage** human gate; actual protection must be independently configured and verified. Only after separate staging authorization and reviewer approval may a maintainer dispatch that workflow. It is intentionally not executable now. Staging is not publication of the intended version, but it reserves that version; treat the stage ID and immutable npm tag as release state.
6. On npmjs.com open **Staged Packages**, locate the exact package and stage ID, wait for npm's malware scan to complete, and review name, version, tag, files, digest and provenance. A maintainer may use `npm stage view <stage-id>` and `npm stage download <stage-id>` on a trusted authenticated workstation and compare the downloaded bytes to the reviewed SHA-256. Do not rely solely on the workflow log. Only after separate publication approval, approve the **intended** staged version with 2FA on npmjs.com or `npm stage approve <stage-id>`. Never approve the bootstrap sentinel. OIDC cannot perform stage review, approval or rejection; those require an interactive maintainer identity.
7. Verify the public npm package version, tarball and `dist.integrity` independently, confirm provenance links to the approved public repository/workflow/source, install the published registry package in clean consumers, rerun API, style, Astro, React, root/subpath and browser checks, and then update downstream lockfiles. Once the intended version is confirmed public and independently verified, an authorized maintainer may reject the sentinel with 2FA (`npm stage reject <bootstrap-stage-id>`). Verify resulting npm state; do not assume the public placeholder or registry history can be rolled back. `/theme` stays supported; deprecation requires a further decision.
