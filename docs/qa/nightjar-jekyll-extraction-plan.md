# Jekyll extraction plan — review only

This is a proposed subsequent operation, not authorization to create repositories, move files, change ownership, publish packages, or deploy sites. The candidates are `martlettheme/jekyll` and `krigsvoldtheme/jekyll`; their availability, administrators and final names must be confirmed before any migration. The observations below describe the workbench at `ea5a180` and the inspected sibling checkouts on 2026-10-29. A later scientific-route integration and subsequent changes may alter paths or evidence; re-inventory the actual approved integration commit before extraction.

## Proposed ownership and synchronization

Use the existing workbench as the **transitional authority** for framework-neutral catalog records, fixture data, schemas, shared behavioral specifications and the paired conformance runner. Do not add a shared repository or package for the migration. Designate the two proposed family repositories as eventual authorities for their Jekyll implementations only after their contents and acceptance gates below are reviewed. Until that handoff, the present generator and its synchronized exports remain authoritative; avoid a period in which two writable copies both claim to be canonical.

Before the handoff, agree on a small documented input contract: the exact workbench commit and paths supplying the recipe catalog, schemas, dashboard fixtures and expected behavior; the exact family implementation revisions; and whether shared Liquid/controller files remain generated inputs or become independently maintained implementations. Prefer a pinned snapshot and an explicit, reviewable update over an unversioned runtime dependency or automatically writing to another repository. Keep family-specific source, layouts and styling independent even when behavior and fixtures are shared. Include source commit identifiers and license notices with copied input. If a generated snapshot is retained in each Jekyll repository, its update must be deterministic and checked for drift; document that edits belong at the designated upstream and do not automatically flow backward.

After handoff, the workbench conformance job can check out the two Jekyll repositories at explicitly recorded immutable commits, build both alongside its Astro and React adapters, and run the existing paired tests. A local or offline mode should accept pre-existing checkouts at those exact commits and verify their identities; never substitute a moving default branch silently. External access, actions checkout permissions and repository visibility must be confirmed. Keep per-family CI able to build and test its own project from a clean clone without a live workbench checkout; the pinned workbench inputs can be included as a reviewed snapshot for that standalone path. The workbench job is the integration gate, not a replacement for family-owned tests. Decide how intentional adapter differences are recorded before removing the current synchronization check.

## Staged migration and acceptance gates

1. **Freeze a reviewed baseline.** Complete and review the stacked workbench PRs first, record the exact source SHA and clean source manifests, and verify current permissions, destination names, licenses, attribution, default-branch protections and designated family maintainers. Inventory the experimental scientific workspace separately from the 50 canonical recipes. Do not change a source of truth in this step.
2. **Prepare disposable candidates.** Assemble each candidate from the approved family export and its chosen provenance/history strategy. Carry the lockfile, local plugin, self-hosted assets, notices, source manifests or equivalent allowlist, safe archive construction, and concise standalone instructions. Review family-specific shell hashes and peer-comparison URLs; do not assume existing preview hosts are permanent. Validate that export generation does not overwrite unrelated host content and that stale generated pages are explicitly removed when the catalog changes.
3. **Run standalone and archive gates.** On clean clones with locked Ruby/Bundler dependencies, build root and `/preview` sites, verify local destinations and fragments, exercise archive rebuild without Git metadata, and check manifest rejection of missing files, symlinks and unsafe destinations. Run Markdown/URL sanitization and Jekyll `--safe` fallback checks. Compare staged file lists and hashes to the approved source; exclude credentials, local dependencies and build artifacts. Validate license and font notices.
4. **Run paired gates.** Pin both candidate revisions in a disposable workbench integration branch. Run catalog/schema and source-drift checks, all 50 routes plus the separately tracked scientific example, dashboard and interaction suites, responsive and no-JS/blocked-script tests, and automated accessibility checks in the engines available to CI. Compare content/semantics and representative visuals *within* each language across frameworks, without requiring Martlet and Krigsvold pixel equality. Record actual browser results, incomplete automated findings and manual assistive-technology work separately; do not infer conformance from the 300-cell inventory alone.
5. **Review handoff.** Produce a file-level ownership map and tested dependency/version pin update; review each family candidate and cross-framework integration as distinct changes. Define who approves fixture updates and how downstream changes flow back. Document recovery: retain the workbench sources and the exact pre-handoff commits and patches until candidate repositories and pinned integration have passed review; a failed candidate means continuing from the old workbench baseline, not publishing a partial migration.
6. **Only in a separately authorized operation:** create or populate approved repositories, establish branch protection and least-privilege CI, open reviewable PRs, and perform the agreed ownership cutover. Preserve old sources through an agreed deprecation window. Any deletion, redirects, archival, release or deployment requires its own approved sequence.

## CI, release and integration safeguards

The workbench portable workflow runs for matching pull requests and pushes to `main`, builds both locked Jekyll projects and performs source, archive, link and browser checks. The workbench `ci.yml` also calls the React reference publication workflow on a successful `main` push; the callable workflow packages and publishes tested references and can open downstream adoption changes. Its manual preparation workflow can likewise invoke publication when explicitly selected on `main`. Thus merging a workbench PR or pushing to `main` can have external release/adoption effects even when a Jekyll extraction is the intended change. Inspect current workflow definitions and repository settings again immediately before any integration; do not infer that a draft PR run deploys, or that a merge is safe merely because this report exists.

The inspected native npm and Astro repositories have workflows triggered by a published GitHub release that run `npm publish` with trusted publishing. Do not create releases, reuse their publish workflows, configure publication credentials, or dispatch a reference publication as part of this planning task. New Jekyll CI should initially grant read-only permissions and run on PRs without publishing, release creation or hosting; explicitly review any later automation and artifact retention. Decide separately whether these projects are examples, distributable source archives, or Ruby gems before choosing a versioning and release mechanism. No package registry name or ownership is reserved by this plan.
