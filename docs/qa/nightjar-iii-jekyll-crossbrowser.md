# Standalone Jekyll dashboard: hosted browser rehearsal

This work is a test-only pull-request workflow, not a release or production-control change. It triggers only on pull requests targeting `nightjar3/jekyll-dashboard-adoption` or the frozen `nightjar/ii-integration-candidate` review branch, grants `contents: read`, persists no checkout credentials, and has no upload, release, publication, deployment, dispatch or downstream adoption step. Browser installation and dependency installation occur on disposable GitHub-hosted runners.

The workflow materializes two local, remote-free candidates directly from the explicitly pinned, locally present workbench guide source commit `d45c1c64df5d189f45790c34344eaa7c293ea9e6`, using the [#46](https://github.com/k3jph/design-workbench/pull/46) materializer. It verifies the deterministic Martlet tree `212297767a5c8ccd5c957b1fd446f62afcb92ab5` and Krigsvold tree `a66856ab8cd568a2a50a22f8099149b0c598fdf2` before capturing each newly generated local commit ID and passing those exact pins to the clean-room consumer. Commits are created locally because they are distinct ephemeral Git objects; a moving branch is never used as the consumer's pin. No remote family repositories are created or consulted.

Chromium, Firefox and WebKit each run the unchanged #53 dashboard consumer: both families, root/subpath builds, guide snippet extraction from the candidate, source-archive guide and consumer-file inclusion, keyboard search and Clear, focus, no-match recovery, static no-JavaScript fallback, blocked and partial initialization, viewport reflow and applicable axe checks. Chromium additionally samples the accessibility tree when JavaScript is truly disabled; axe itself cannot run in that state. The hosted workflow reports its individual engine results through CI; a workflow definition or queued job is not a pass. Manual assistive-technology, physical print, complete visual review and the existing Firefox/WebKit contrast incompletes remain open.

Reproduction uses the existing locked npm and Ruby dependencies and the [standalone adoption evidence](nightjar-iii-jekyll-dashboard-adoption.md). An independent local materialization of the pinned guide source reproduced both expected trees, and the identical consumer is run separately with the system Chromium. The candidate is assembled by cherry-picking the local-only #46 materializer onto #53 to make the workflow self-contained; the original branches and their source authority remain unchanged.
