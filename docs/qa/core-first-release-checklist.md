## Exact trusted-publisher and workflow checks

1. An npm scope owner confirms authority over `@martlet/core` and `@krigsvold/core`, version availability, and the bootstrap procedure supported for the first trusted publication. Do not stage a package as a test: staging is a public registry mutation and requires its own authorization.
2. Review the existing legacy `@martlet/theme` and `@krigsvold/theme` publisher bindings after the organization and repository renames. Preserve a supported publication and consumer maintenance path; do not assume old GitHub names or OIDC bindings redirect.
3. With separate authorization and at the appropriate time, configure or confirm trusted publishing for the exact target identities: npm `@martlet/core` ↔ GitHub owner `martletdesign`, repository `core`, workflow `publish.yml`; npm `@krigsvold/core` ↔ owner `krigsvolddesign`, repository `core`, workflow `publish.yml`. The inspected workflow jobs have no GitHub environment field; if an environment is introduced it must match the binding and needs separate production-control approval. Record account/scope ownership and verify the npm UI's actual configuration without exposing tokens. New, unvalidated publisher configurations may expire after 48 hours; coordinate any configuration with the authorized publication window.
4. The current workflows run `.github/workflows/verify.yml`, then check out the published release tag, set up Node 24 and npm 11, require `v<version>`, matching package/source versions, matching renamed repository URL and ancestry from `main`, run `npm ci`, build and tests, require a clean tree, and execute `npm publish --access public`. A GitHub prerelease selects npm tag `next`; a non-prerelease selects `latest`. The workflow requests `id-token: write` and enables npm provenance when the repository is public. It does not check the package name against an independently configured allowlist: verify the exact manifest and workflow at the approved release commit.
5. Approve the exact release version, tag, distribution tag, package contents and integration sequence. Review changes to `private`, source and lock versions, generated files, and all downstream pins. Separately authorize each merge into `main` and each GitHub release/publication. Do not force-update existing tags. Confirm that no downstream automation or site adoption will deploy as a side effect.
6. After an authorized, reviewed release change removes `private`, build and pack using the intended release toolchain and file modes; record the new bytes and SHA-256. Rerun package, archive, compatibility, framework, root/subpath and browser checks against **those bytes**. The private tarball hashes above cannot be reused after changing the manifest, mode, version, docs or generated output. The checked-in workflow currently packs again during `npm publish`; maintainers must verify its actual published bytes and provenance rather than assume byte identity with a pre-release tarball.
7. Following a separately authorized publication, independently install from npm in clean consumers and verify resolved registry identity, SRI/integrity, package contents, ESM/CJS and CSS exports, licenses and provenance. Then migrate Astro/React lockfiles and release them under separate approvals, followed by workbench/site adoption and deployment approvals. Do not deprecate or unpublish `/theme` without a further decision.
