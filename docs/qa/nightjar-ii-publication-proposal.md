The frozen candidate is `5138a89fc2956d9019d5bd720c987b8b9e24533b`; at review, its first parent and remote `main` are `aafd9a8443e0c6cdc4afd6f973a605faa74b8f2c`. PR #20 remains a review baseline, not authority to integrate. **Keep the candidate on a non-main branch until an independently verified publication control or explicit authorization for all resulting external actions exists.**

## What needs a gate

On the inspected main, `.github/workflows/ci.yml` calls `reference-release.yml` after verification on a push to `main`. Its `package` job builds reference archives and uploads a GitHub Actions artifact, `test-archives` tests them, `publish` creates a commit-qualified tag and publishes a GitHub prerelease, and `adopt` can write and merge host adoption PRs and wait for Cloudflare production deployments. The archive/tag/release happens **before** adoption credentials are checked. Gating only `publish` is therefore too late to prevent release-pipeline archive creation or artifact upload. `prepare-release.yml` can also call the reusable reference workflow when manually dispatched on main with `publish_references=true`; `publish.yml` can call it after a published `react-v` prerelease and independently runs `npm publish` for each React family. Review the latter separately: by the time a published-release trigger fires, the triggering release already exists. There is no automatic guarantee against a direct manual release, a different workflow, an older queued attempt, GitHub App, webhook or external host.

**Scope distinction:** ordinary PR/main verification already calls `package:preview`, packs npm packages and may upload Actions test artifacts. These are internal build/test artifacts, not the reusable release pipeline's public prerelease, but they are still archives/artifacts. The proposed reference gate below only covers the reusable reference-release pipeline. If the approval requirement means *any* archive creation or artifact upload, including local verification, it is insufficient: separately redesign and gate those verification steps, or avoid the main push. Do not describe this proposal as satisfying that stricter interpretation until its full effect graph is reviewed. The existing named workflows are not an inventory of external hosting integrations.

## Proposed design, not an active change

1. In the reusable `reference-release.yml`, insert an explicit, environment-protected approval job **before `package`**, and make `package` depend on its successful completion. Keep `test-archives` dependent on `package`, `publish` on `test-archives`, and `adopt` on `publish`; prohibit bypass paths such as `always()` or conditional paths that run effects after rejection, failure, cancellation or skip. Check that every new reference-workflow caller still enters this central job. The effect boundary is before `npm run package:preview` and `actions/upload-artifact` in the reusable `package` job, as well as all later effects.
2. Provision a dedicated environment with required reviewers, self-review prevention, no administrator bypass, and a deliberately restricted branch/tag policy **before** making the workflow change eligible for main. GitHub can create a missing environment without those protections: the environment name by itself is not fail-closed. Verify plan/visibility support, reviewer availability and administrator controls in the actual repository. Require an environment-scoped bootstrap sentinel checked before effects, and confirm there is no repository/organization secret with the same name that could act as a fallback. The sentinel only catches a missing/unconfigured environment; it does not prove that reviewers or bypass settings remain correct if an administrator removes them. Protect configuration and workflow edits with separately reviewed access/rulesets and independently audit those settings.
3. The environment must be attached to an ordinary job **inside the called workflow**; a `uses:` job that calls a reusable workflow cannot itself receive an `environment` key. GitHub's context for a reusable workflow belongs to the caller: a main push, a manual dispatch and a published-release/tag caller can present different refs. Test the actual caller/ref combinations and branch/tag rules; do not assume all calls have `refs/heads/main`. For the release caller, the existing prerelease has already been published before this gate. Whether that path should continue at all requires a separately reviewed release policy and protections on the independent npm `publish.yml` path.
4. Choose deliberately whether GitHub deployment records are acceptable. Current GitHub documentation says `deployment: false` can suppress a deployment object while preserving required reviewers, but it conflicts with custom deployment protection rule apps; verify actual runner/service support and behavior in a disposable repository. This proposal does not create a deployment or approve a review.

### Illustrative inactive patch (not applied)

The following is a design sketch, **not** a drop-in security control or an authorized workflow change. It must not be pasted into production before the prerequisites and independent adversarial tests below. The repository-unique sentinel name and its contents must be chosen and configured by an authorized administrator without exposing them; this sketch intentionally leaves that configuration absent.

```yaml
# Illustrative jobs inside reference-release.yml, not an active workflow.
reference-approval:
  runs-on: ubuntu-latest
  environment:
    name: reference-release-approval
    deployment: false
  permissions:
    contents: read
  steps:
    - name: Require the pre-provisioned environment sentinel
      env:
        REFERENCE_ENV_SENTINEL: ${{ secrets.NIGHTJAR_REFERENCE_ENV_SENTINEL }}
      run: test -n "$REFERENCE_ENV_SENTINEL"
package:
  needs: reference-approval
  # retain the existing package steps; no alternate effect path
```

This arrangement can fail closed for an absent sentinel **only if** no same-named repository/organization secret can satisfy it. It does not cryptographically prove the environment's current reviewer/bypass policy, does not stop admins from weakening policy, does not protect a release already published, and does not gate unrelated workflows. A protected environment has up to six configured reviewers but only one needs to approve; do not assume a two-person quorum. These limitations are part of the approval decision, not exceptions to be silently accepted.

## Nonpublishing validation and authorization checklist

No step below authorizes a production change. The first two are available now; the rest require separately authorized use of a **disposable** repository/environment, or a separately reviewed production-control change as explicitly stated.

1. Run `python3 -m unittest docs.qa.tests.test_nightjar_publication_graph` from this branch (requires PyYAML). It inspects the checked-in reusable workflow's job dependency graph, proves that the current `package` path lacks a gate, and applies an in-memory proposal. Adversarial fixtures remove the gate, remove a dependency, add an unconditional bypass, misconfigure the environment or reuse a fallback sentinel. The model has no network and cannot invoke, modify, publish or deploy anything. It validates only graph assumptions, not GitHub's enforcement, dynamic workflow expressions, all hidden effects or an administrator's settings. It intentionally does not edit `.github/workflows`.
2. Review all job commands, actions and called scripts for archive creation, tag/release creation, remote writes, artifact uploads, npm publishing and deployment. Re-run the static check and compare all callers/effects to the actual planned diff. A passing modeled graph is not evidence that all effects have been identified.
3. If the user separately authorizes an isolated GitHub experiment, pre-create a disposable repository and a protected test environment with **fake data and no production credentials or external integrations**. First record environment configuration and baseline public/private artifacts, releases, tags, deployment records and target repositories. Prove missing environment/sentinel, missing rules, revoked approval, self-approval, bypass, disallowed ref, cancellation, timeout, retry and old-workflow rerun cannot reach any fake-effect job; prove a separately authorized approval can reach only a harmless local marker. Check all three reference callers and release/tag ref handling. Run no actual `publish.mjs`, `adopt.mjs`, `npm publish`, real deployment or network-mutating fake effect. Compare evidence before/after; a local model is not this hosted experiment.
4. Before a separately authorized production change, an administrator must record actual plan/visibility, pre-create the protected environment, choose reviewers and enforce self-review prevention/no bypass, define exact branch/tag rules, audit sentinel-name collisions and who can change rules/secrets/workflows, inspect external Cloudflare/GitHub Apps and all callers, and enumerate running/queued/re-runnable old workflow attempts. Validate failures and approvals against the exact reviewed workflow commit and repository settings, documenting who has authority and evidence for each gate. Re-review if any configuration, code, ref or repository visibility changes. Never rely on missing adoption secrets, cancellation races or skip-CI markers.
5. Human review must also decide whether and how independently triggered npm releases and manual GitHub tag/releases are protected, and whether internal CI archives are permitted before approval. Only after an independently verified control and separately authorized integration, or explicit authorization of all publication/adoption/deployment effects, may an operator consider a **single** integration of the complete tested candidate. Recheck exact main/head/branch rules, compare the integrated tree and rerun checks. Merging #18 alone is not equivalent to the fixed stack.
