# Nightjar III publication boundaries and four-repository cutover — proposal only

This is a nonproduction review plan, not an active control or an authorization to change workflows, protected environments, repositories, release channels or hosting. It extends the [Nightjar II proposal](nightjar-ii-publication-proposal.md), whose single pre-package approval is explicitly **not active or verified**. The frozen workbench candidate is `80a5635abe4de7a07a1983de0b3ef796b101e047`. Workbench `main` observed at `aafd9a8443e0c6cdc4afd6f973a605faa74b8f2c` is an earlier state and must be rechecked immediately before any future action.

## Why an additional decision is necessary

The prior proposal models one approval before the reusable reference workflow's `package` job. That is a useful boundary for preventing an ungated reference archive, but it does **not** implement separate authorization for later publication, host adoption and deployment. In the candidate's current `.github/workflows/reference-release.yml`, `publish` follows `test-archives`, and `adopt` follows `publish`; `scripts/reference-release/adopt.mjs` can create a host branch and PR, merge it after checks, and only then wait for a Cloudflare deployment. A single pre-package approval could therefore permit every later action, including merges and deployment, without another decision. Source-site PR creation itself may trigger external previews; whether it does so depends on hosting settings not observable from this repository.

The proposed pre-package gate also does not cover independent npm publication on a `react-v` published prerelease, nor undo the initiating release that already exists when that event fires. Each family's existing theme and Astro repositories has its own published-release-triggered npm workflow. No `main` merge is safe merely because a diagram or local model exists. Ordinary workbench verification also creates local package archives and may upload Actions artifacts. The operator must explicitly decide whether those **internal** test artifacts fall within the separately authorized boundary; if all archive uploads are prohibited, the Nightjar II release-pipeline gate alone is insufficient. Do not treat this distinction as permission to publish a reference archive.

## Effects and independent authorization boundaries

The following decisions may be reviewed together, but approval of one is not approval of the next. The referenced gates are **requirements for a future separately reviewed design**, not configured environments or working production controls.

| Decision and immutable subject | Effect to block before the decision | Why a later check is insufficient |
| --- | --- | --- |
| Integrate workbench code: reviewed merge tree, current main SHA and exact workflow revision | Main-branch write and any `push`-triggered jobs; include an explicit decision on internal CI archive/artifact upload. | The existing main push calls reference packaging. The complete stack must land atomically after an independently verified safe control; do not merge #18 alone or rely on missing adoption credentials. |
| Release a reference: exact tested source commit, archive hashes, target tag, release visibility and asset names | The release-pipeline package/artifact boundary if required, then `git/refs` creation, release creation/asset upload and publication. | `publish.mjs` may create the tag and upload release assets before host adoption begins. A downstream adoption gate cannot undo those effects. |
| Publish a package: exact family, package name, new version, tag, tarball digest, registry and provenance identity | Registry `npm publish`, RubyGems publication if ever proposed, and any release event that triggers it. | Workbench's React npm job is independent of the reference gate. The published `@<family>/react@0.1.0` bytes already differ from candidate packages of the same version; a new reviewed version is needed. No Ruby gem or registry ownership is implied by a Jekyll rehearsal. |
| Adopt into a host: each family, immutable source/reference hash, target repository, expected base and exact PR diff | Creation or update of host branches/PRs **and** any previews they trigger; separately, merge. | `adopt.mjs` currently creates a PR and auto-merges it after checks; its single matrix job does not provide per-family human approval. An approval after the merge cannot stop a host deployment. |
| Deploy: each family, exact host commit, target environment and verified rollback | External host build/deploy triggers, Worker routes, assets and production promotion. | Cloudflare is polled after the host merge; successful observation is not authorization or a preventative gate. External branch/preview hooks and deployment protections must be independently verified before any write that can trigger them. |

Use scoped attestations or equivalent review records that bind each decision to its exact commit, artifact digest, family, repository, target environment and intended action; reject stale, revoked, wrong-family, wrong-target or superseded decisions. This is a proposed acceptance criterion, not a claim that an environment approval automatically binds all those fields. Decide whether creating a GitHub deployment record is itself permitted. Any concrete implementation must separately examine plan/visibility support, reviewer and bypass semantics, authority to edit policies, environment-name auto-creation and same-name secret fallbacks described in the Nightjar II proposal.

## Four proposed repositories: prepare, then separately authorize

The potential names `martlettheme/jekyll`, `krigsvoldtheme/jekyll`, `martlettheme/react` and `krigsvoldtheme/react` are proposals, not reservations or existing target authorities. Keep their offline candidates separate and record source workbench SHA, candidate tree and artifact hashes, complete file mapping, attribution/notices, dependency lock and independent build/consumer evidence. Decide for each the maintainer, visibility, allowed Actions permissions, test-artifact retention, branch/ref protections and who can alter workflows or publishing credentials. Check organization-level automation, inherited apps, branch-preview hooks and trusted-publishing associations before any repository creation or first push. A repository can inherit integration effects not visible in its source tree.

1. **Review dry runs:** verify each candidate independently, root/subpath and archive rebuild for Jekyll; built package/types/CSS plus packed consumers for React; all required pinned conformance inputs, releases and cross-framework fixes. Preserve frozen workbench sources and versioned backup patches. No remote creation or source-authority transfer occurs in this step.
2. **Separate repository-creation authorization:** approve exact names, visibility, administrators, initial history/snapshot and permitted configuration. Before first remote write, inspect the organization policy and external integrations; configure only the separately authorized read-only verification behavior. A plan cannot pre-authorize activating protected environments or production settings.
3. **Separate initial-population and PR authorization:** compare the exact tree to the reviewed offline candidate, check no tokens/secrets or unrelated content, and use nonpublishing CI with minimal permissions. Record any internal artifact uploads and ensure no external preview or deployment will trigger without its own authorization. Do not grant OIDC/trusted-publishing, release, host-adoption or deployment permissions merely to run tests.
4. **Separate source-authority handoff:** approve the new single owner for each implementation file, freeze/pin the shared fixture contract, compare both families, establish review rights and rollback owner, and verify the old workbench renderer paths and shared models remain available until all consumers are migrated. The workbench stays the neutral contract/fixture/conformance authority unless separately changed. No delete, redirect or archive follows automatically.
5. **Separate version/release, adoption and deployment decisions:** resolve existing registry versions first, publish only explicitly authorized immutable artifacts, update consumer pins in reviewable changes and prove all required tests at exact commits. Verify the host's external triggers and require the particular deployment authorization **before** a merge or other action that triggers it. One family's success does not authorize publishing or deploying the other.

At every boundary, stop on uncertainty about the current branch head, source tree, token identity, environment enforcement, external hook or artifact hash. Retain the old authoritative workbench paths and exact previous pins until the agreed cutover succeeds. Rollback means a separately reviewed and authorized restoration of pins or authority; a published version, tag, download, external deployment or cloned repository cannot be assumed retractable. Do not force-move tags, overwrite registry versions, delete evidence, or infer permission for a later step from an earlier approval.

## Nonpublishing checks and limits

Run `python3 -m unittest docs.qa.tests.test_nightjar_publication_graph docs.qa.tests.test_nightjar_iii_publication_boundaries`. The first suite checks the existing release graph under **supplied** policy assumptions. The second demonstrates that a single upstream gate can satisfy that model while leaving publication and adoption without separate gates, and tests an illustrative multi-boundary graph plus missing/bypass cases entirely in memory. These tests do not change workflow files or call GitHub. They do not verify the future Cloudflare gate, externally configured previews, organization settings, old workflow attempts, identity binding, four new repositories or registry behavior. A green local model is evidence only about its stated graph assumptions.

Before separately authorized production changes, an administrator must inventory all actual callers, old queued/rerunnable workflow revisions, releases and tags, each repository's permissions/apps, artifact destinations, trusted-publisher configurations and external Cloudflare/preview hooks. Validate fail-closed behavior against the exact reviewed workflow and actual repository settings, including missing controls, stale approvals, missing/mismatched sentinels, disallowed refs, retries, cancellation and independently scoped family/target approvals. Use no production credentials, real release endpoints or deployment during nonpublishing experiments; if an isolated remote experiment itself requires repository or environment creation, obtain separate authorization first.
