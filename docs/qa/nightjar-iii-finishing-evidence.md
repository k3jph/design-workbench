## Input controls and limits

An opt-in identity check now binds package name, exact version, and selected archived source SHA-256 values before build. It rejects missing files, mismatched family/version and altered checked bytes; the Git pin must already resolve to a full commit. These checks have unit regressions, including a same-name wrong-version and a changed export. This does not prove all files or arbitrary build commands are correct. A manifest without `input_checks` retains the previous behavior, and a manifest author can select incorrect expected bytes. The result still says `declared_input_consumption: not_verified`.

On Node 24.19 and local Chromium, the new integration negative script created disposable commits in local clones and changed its expected source hash to match each intentional mutation. The Martlet and Krigsvold React gallery builds then failed specifically because `DataTable` was not exported; the two Astro gallery builds failed specifically because `Button.astro` could not be resolved. Thus the particular gallery commands exercised those package exports; this is not proof for every export, nor independent ownership of the gallery. A real Martlet React positive run with the input check completed 50 static routes at `/` and 50 at `/preview`; it used the existing workbench gallery and warm offline npm cache. It is bounded static evidence, not accessibility or behavioral conformance. A nonexistent commit, a conflicting version, a wrong source hash and an absent source file separately failed in the runner before build. A corrupt local tarball failed `npm install --offline` with `TAR_BAD_ARCHIVE`; an empty cache failed `npm install --offline` with `ENOTCACHED`. Offline npm mode and the previous observed zero network syscalls do not enforce network isolation for arbitrary trusted build commands; a blocked-network sandbox test remains open.

## Proposed safe handoff and rollback

1. Before creating a remote, review four tree hashes, licenses and notices, fixture provenance, a nonpublishing read-only CI proposal, complete consumer and negative tests, and nominate family maintainers. Approve each proposed repository name, visibility and creation separately. No remote exists as a result of this rehearsal.
2. For each fixture update, review a workbench commit and its catalog/dashboard hashes, generate into a new local candidate, compare the attributed file map and deletion policy, review family identity and run root/subpath, archive, consumer and pinned conformance tests. The workbench remains the only contract/fixture owner. Current Jekyll seeded overlays and stale-page deletion policy require an explicit maintainer decision; there is no tested automatic cross-repository fixture-update mechanism yet.
3. Keep current workbench source authoritative until a separately approved, simultaneous owner handoff records the exact family source commit and the workbench's pinned input. Prevent dual edits via an agreed freeze and reviewed compatibility window; do not remove workbench paths during rehearsal. Verify rollback by rebuilding the prior source and prior consumer lockfiles before cutover.
4. If pre-handoff validation fails, retain workbench authority and abandon the local rehearsal. After an authorized future handoff, revert consumer pins and rebuild from preserved workbench sources or previously published immutable package versions; do not overwrite a published version, delete history, or force-push. Restore ownership only through an explicitly approved reverse handoff. Package tags, host adoption and production deployment require separate approvals and a tested publication-control gate; no such gate is active today.

Remaining gates include exact-head portable CI, independent six-implementation acceptance, a deterministic tested fixture update, administrator-only Dependabot records, 18 Firefox plus 18 WebKit inconclusive axe contrast nodes, manual assistive technology, physical print and representative visual review. Neither a clean npm audit nor a successful route check closes these gaps.
