# Framework documentation snapshots: contract proposal

This is a local contract and verifier for the requirement in [issue #63](https://github.com/k3jph/design-workbench/issues/63). It does not publish archives, implement framework sites, or change hosting. Each family and framework owns its own catalog and release history. Framework versions are independent of core versions.

Each immutable `/docs/v/<framework-version>/` directory contains a `manifest.json` and the complete HTML, CSS, JavaScript, fonts, examples, and other assets it uses. Manifest schema 1 records `family`, `framework`, `docsVersion`, `basePath`, `implementation` (kind, name, version, tag), exact `core` name/version/npm SHA-512 integrity, `source` repository/commit/tag, fixture provenance (`source: repository` or an exact `workbenchCommit`), `toolchain`, UTC `createdAt`, `indexing: noindex`, and a `files` array of `{path, size, sha256}` for every file except the manifest itself. The manifest's SHA-256 is recorded in the catalog to avoid a self-referential digest. Jekyll uses its Git repository and tag, not an invented npm identity. Every archived HTML file must contain a robots noindex directive.

Each catalog has schema 1, `family`, `framework`, `latestStable`, and `versions` entries containing `version`, `channel` (`stable` or `prerelease`), `supported`, `manifestSha256`, and relative `topics` present in that snapshot. A supported latest pointer must identify the newest supported stable entry. Retiring a version may change its support state but must preserve its manifest digest and topic paths. `versionNavigationModel` supplies neutral link and status data for each framework's accessible selector, accepting a root or preview/subpath prefix. It retains the topic when present and falls back to that version's index when absent. Framework adapters must render the active version, latest stable, prereleases separately, unsupported status, and accessible keyboard navigation.

Run `node scripts/docs-versions/generate.mjs metadata.json snapshot-dir` to produce a manifest on stdout; it hashes the actual files and refuses an existing manifest. Capture stdout **outside** the snapshot directory first, then install it as `manifest.json` using a no-overwrite operation; redirecting directly into the snapshot creates the file before generation and is rejected. Record its SHA-256 in the catalog. Run `node scripts/docs-versions/verify.mjs catalog.json archive-root [previous-catalog.json]`. The archive root contains a directory per version. The verifier checks manifest/catalog identity, a catalog-pinned manifest hash, file inventory and digests, no unlisted files or symlinks, HTML noindex, topic presence, version identities, and history against the supplied previous catalog. `node --test scripts/docs-versions/*.test.mjs` covers both families and three framework identities plus tampering and fallback cases. A first release has no previous catalog; later releases must obtain the previously published catalog from an independently trusted immutable source and pass it explicitly. The verifier cannot by itself prevent a publisher from omitting the previous catalog, rewriting storage, or replacing both the old catalog and archives. Production authority, immutable-object enforcement, and separately controlled latest-pointer advancement remain essential.

`createSnapshot` in `snapshot.mjs` supplies a local nonpublishing building block: it checks the supplied baseline catalog digest, verifies every old archive, checks the exact core version and integrity against the build lock, reserves a new version directory without overwrite, and writes and verifies a manifest. It returns a pending catalog entry and does not modify the baseline or advance `latest`. It requires an explicit empty baseline for a first release. This local filesystem guard is not proof of remote object immutability; the baseline digest and history must come from independently protected production storage before activation.

## Integration gates

The Astro starter archive candidates are [Martlet #9](https://github.com/martletdesign/astro/pull/9) and [Krigsvold #9](https://github.com/krigsvolddesign/astro/pull/9), with release integration in each repository's #10. They build five starter pages against exact core pins, exercise an accessible version navigation, and test root and preview paths. They do not establish complete reference-site content, authenticated immutable storage, or production serving. React and Jekyll adapters, selectors, pinned builds and browser checks remain unimplemented; neither standalone repository currently contains source. Canonical latest routes, cross-site links and real-site navigation remain open. Archive publication and `latest` promotion must be separate operations with tested pointer rollback; they need no routine human gate once authorized release policy is in force. Do not rebuild historical URLs from current main or dependencies. Manual assistive-technology and real-device results must be reported separately.

One possible authoritative archive backend is an immutable GitHub Release asset in each framework repository. GitHub documents that published immutable releases lock their assets and tag, and recommends creating a draft and attaching all assets before publication. An authorized workflow could verify historical release attestations and assets, build the next snapshot, publish and verify npm first, then create a draft GitHub Release, attach the snapshot, publish the release, and verify the asset. This ordering satisfies the package-before-GitHub-Release rule and does not add a routine human gate. It must still handle failures after npm publication without republishing. [GitHub immutable release behavior](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) and [release verification](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity) are the authoritative references.

This option is not implemented or selected for production. An immutable GitHub Release can still be deleted, and a release asset archive alone does not serve stable `/docs/v/.../` HTML routes. Account for repository/release deletion, independent retention, a read-only serving mechanism, and protected catalog/latest-pointer updates before relying on it. Do not enable release immutability, create releases, deploy a serving layer, or change hosting without the applicable authorization. The Astro release drafts therefore deliberately fail closed until an authenticated immutable archive publication and verification adapter is implemented and tested.
