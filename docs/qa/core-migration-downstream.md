## Verification boundaries

The separately tested legacy and core React clean rooms do not install one identity as a stand-in for the other. Negative checks reject a wrong core archive digest and a mismatched family source tree. On the corrected selected inputs, [workbench run 41229530178](https://github.com/k3jph/design-workbench/actions/runs/41229530178) passed the reconstructed packed React/core suite in Chromium, Firefox and WebKit at `3715c8097db58b44439b66a357bd23ace5496e53`. The PR workflow also checks the actual permanent React #66 source and site patch candidates; use its exact-head results rather than assuming completion.

The site builds verify the original React reference archive and provenance before extracting it. Only its generated site copy is rebased for the site prefix; the source archive and canonical Markdown copies remain unchanged. The static verifier checks every server-rendered site page; the embedded React reference is an SPA and is checked after browser rendering, including route, heading, internal links and local asset loads. Manual accessibility and visual review, and the existing incomplete Firefox/WebKit contrast checks, remain separate from automated passes.

## Approved-release sequence

1. Confirm npm scope ownership, final versions, the core contrast changes and artifact modes. Verify the existing `/theme` publisher bindings and maintenance path after the GitHub organization/repository rename. Do not infer ownership from a 404.
2. Secure explicit approval for each live trusted-publisher configuration and core publication. Coordinate OIDC's validation window with the actual separately approved release. Prepare final core release commits, remove private guards only with approval, rebuild, hash and rerun all tests against the exact publishable bytes. Publish core and independently verify the installed registry artifact, integrity and provenance.
3. Replace local fixture lock resolutions with the verified registry values. Rerun Astro and React checks, then separately approve framework releases. The candidate React 0.2.0 and Astro 2.0.0 are proposals, not claims of published availability.
4. Verify external preview/deployment triggers, update site and workbench registry references and lockfiles, repeat root/subpath and browser checks, then seek separate approvals for adoption and deployment. Keep `/theme` available; a compatibility policy or deprecation is a separate decision.

No package staging, release, publication, merge, production-control change or deployment is authorized by this preparation.
