This is a local, attributed snapshot exercise, not authority transfer, a release, or an approval to create remote repositories. The source is the frozen Nightjar II candidate `80a5635abe4de7a07a1983de0b3ef796b101e047`, workbench tree `b65bf1fd31c277048e7e4542130f34f7b0416ed4`. Both package implementations remain owned by the workbench until a separately approved cutover. Prospective repository names are unreserved.

## Reproduce and validate

1. In a workbench checkout with the frozen commit available locally, run `node scripts/nightjar3/react-extraction.mjs --out /absolute/path/to/a/new-directory`. The destination must not already exist. The generator reads source directly from the pinned Git object, refuses missing lockfiles, and does not fetch, use moving branches, mutate the checkout, initialize remote repositories or publish. Its checked-in locks are for the exact generated manifests. `node --test scripts/nightjar3/react-extraction.test.mjs` checks the exact source bytes, public manifest contract, private guard, lock copies and refusal to overwrite. A shallow checkout must first obtain the exact pinned object through an authorized process.
2. In each resulting family directory run `npm ci --ignore-scripts && npm run build && npm pack --ignore-scripts`. Both local builds passed under Node 24.19, and `dist/index.js`, `dist/index.d.ts` and `dist/styles.css` were byte-equal to builds from the frozen workbench packages. The theme remains a separately resolved package and retains its font dependencies and licenses. The lock has 29 Martlet and 28 Krigsvold dependency entries including platform/optional entries; this count is not an installed production size.
3. Both local snapshots were committed separately, exported with `git archive` without `.git`, then independently installed with `npm ci --offline --ignore-scripts` and built/packed successfully using this environment's **already populated npm cache**. This does not prove a cold machine can install without fetching its dependencies, cross-platform reproducibility, or that every transitive dependency is vendored.
4. The resulting tarballs installed into a separate temporary React consumer and rendered all 22 exports, including Field, ErrorSummary, Pagination, Tabs, Article and other documented components. With those tarballs in one directory, set `NIGHTJAR_REACT_ARCHIVE_DIR=/absolute/archive/directory PLAYWRIGHT_EXECUTABLE_PATH=/usr/bin/chromium` and run `npm run test:dialog-consumer`, `test:pagination-consumer`, `test:error-summary-consumer`, `test:fields-consumer` and `test:tabs-consumer` separately. All passed for both candidate tarballs in Chromium, including Dialog close/reopen, Pagination and iframe focus, ErrorSummary targeting and fragment fallback, Field descriptions and SSR/hydration, native reset/no-JS disclosure, and StrictMode dynamic Tabs. The existing scripts resolve workspace packages when the variable is absent. The SSR harness uses the same React installation as its consumer to avoid a duplicate React dispatcher. A packed Field run initially exposed that harness mismatch and passed after correction; a default workspace test initially failed because workspace packages had not been built, then passed after `npm run build --workspaces`.
5. A second generator run produced byte-identical source, metadata, build script and locks. `npm pack` generated identical SHA-1 values across the original and no-Git offline rebuild in this environment; the comparison is not a claim of universal cross-platform archive reproducibility. The separate adoption workstream must inspect actual clean-room developer use. The full 50-recipe gallery is a workbench application, **not present in these packages**, and package tests alone do not prove gallery conformance.
6. `NIGHTJAR_REACT_ARCHIVE_DIR=/absolute/archive/directory PLAYWRIGHT_EXECUTABLE_PATH=/usr/bin/chromium node scripts/nightjar3/test-packed-shell-table.mjs` passed for both families. It checks a composed AppShell and DataTable from the supplied archives, skip-link focus, table header semantics, a keyboard action, containment at 320px and an axe scan. An initial test harness attempt used Playwright's convenience `browser.newPage()` that axe rejects; using an explicit context corrected the harness without weakening assertions. This is a bounded application, not a complete dashboard or manual accessibility assessment.

## Published-version collision and release gate

The registry already contains `@martlet/react@0.1.0` and `@krigsvold/react@0.1.0`, but neither represents this frozen workbench candidate. On the recorded registry comparison, published versus candidate `dist/index.js` SHA-256 was Martlet `f27188d009cf8fd51b520fac26a2416f9133090f7eaeb2497ff775bf1c0a4713` versus `3f10e0cc5e539eeac6ef77176eb940d7a520c79469cc99d70a4cf3832c4a0a43`, and Krigsvold `facb54af528af71aa29f5bc806e002633278780edc19e2464c5102f168ae418a` versus `dc330ba32950422b093c2bf5e2a7e41e9aa981ee8ae423fa6154ccc47c7a6c34`. Their CSS and declaration outputs also differ; the workbench Field includes optional `hintId` and `errorId` absent from those published declarations. Treat this same-version collision as a **hard publication and cutover blocker**. npm versions are immutable: maintainers must review the complete API and visual diff, select new unused versions and migration semantics, and authorize any eventual publication. Never replace or imply equivalence with existing 0.1.0.

## Proposed future CI and cutover

A draft-only, pull-request-triggered workbench rehearsal workflow at `.github/workflows/nightjar-iii-react-rehearsal.yml` builds private candidates and exercises the packed consumer suites in Chromium, Firefox and WebKit with `contents: read`, no release/publish credentials, no production environment and no artifact upload. It is not present on main and makes no production-control change. Its syntax and nonpublishing matrix were checked locally. GitHub did not list a run for the newly added workflow at initial PR head `f26a7c7`; its actual hosted triggering and exact-head results remain unverified. A future independently authorized family repository could use a similar locked build and explicitly pinned workbench contract revision; that family workflow is a proposal, not an activated control. Current independent packed browser execution recorded here covers Chromium only; the frozen workbench passed wider three-engine component suites, but those results are not a new three-engine test of these extracted archives. Further DataTable and AppShell state coverage, framework-wide parity, manual AT, long-content visual review, install footprint and source-asset distribution require standalone-consumer follow-up.

Before any cutover, select a single owner for source and release process, resolve the version collision and compatibility contracts, attribute history, verify independently pinned conformance, review licenses/dependency and token ownership, and exercise rollback with no live effects. Require separate human approval to create/populate each remote, to transfer authority, to merge, and separately to publish or repoint any consumer. A staged rollback keeps existing published packages and workbench sources pinned and restores prior consumer versions/configuration; it must not require deleting immutable npm versions or force-pushing history. No remote repo was created, and no package, archive, tag, deployment or release was published by this rehearsal.
