# Nightjar II component audit — dynamic tab focus

This review builds on frozen candidate `5138a89fc2956d9019d5bd720c987b8b9e24533b`; it does not change that candidate or imply publication of the experimental React packages. The audit inspected the paired `Field`, `Dialog`, `Tabs`, `Pagination`, `ErrorSummary`, `DataTable` and `AppShell` implementations, their documented contracts and existing consumer regressions. The new fix is limited to `Tabs`.

## Reproduced defect and change

For a controlled tabset, a caller can asynchronously remove a tab or mark it disabled. Before this change, when that tab had keyboard focus, Chromium moved focus to the document body. The selected panel remained visible, but the person's next keyboard step lost the tabset's location. On the frozen candidate, the packed-consumer regression in `scripts/test-tabs-packed-dynamic.mjs` failed for **each** family when disabling the focused tab. An additional standalone reproduction observed the same loss when removing it. This was demonstrated in Chromium 151; it is not a claim about all browsers.

Both experimental React packages now transfer focus to the selected enabled fallback if the focused tab is removed or disabled and that update would otherwise leave focus on the body or the disabled tab. Ordinary blur clears the remembered tab, and a subsequent update does not take focus from an outside control. If all tabs become unavailable, there is no enabled fallback and the caller remains responsible for an appropriate recovery target. The change does not alter selection, callback semantics, family CSS, geometry, typography or source-specific visual roles.

## Verification

`npm run check` passed, including the workbench build, documentation and 110 Node tests. `npm run test:packages` installed and rendered both packed packages. With `PLAYWRIGHT_EXECUTABLE_PATH=/usr/bin/chromium`, `npm run test:tabs-consumer` passed the existing manual activation, keyboard, two-tabset and axe checks, plus the new **packed** consumer regression for both families. The new check installs each locally built tarball into its own consumer and covers focused-tab disabling and removal, selected-tab fallback, React Strict Mode, unrelated focus and an intentional blur before an update. The same command is already called by workbench CI for Chromium, Firefox and WebKit; the latter two have not been run locally and need hosted results. No screenshots or visual baselines were changed.

The existing workspace-consumer checks were also rerun on system Chromium for both families: `test:dialog-consumer` passed native/Escape/controlled close, rapid reopening and focus; `test:pagination-consumer` passed boundary and external-change focus; `test:error-summary-consumer` passed focused targets, native-fragment fallback and modified links; and `test:fields-consumer` passed SSR/hydration descriptions, reset and no-JavaScript disclosure. These are workspace-consumer runs, distinct from the new packed-tabs regression. The packed package SSR/export check does not by itself establish `DataTable` or `AppShell` browser behavior; their prior workbench evidence and known one-shell-per-document contract remain relevant. These bounded checks do not establish screen-reader support.

To reproduce the before case, use a separate checkout at `5138a89`, copy `scripts/test-tabs-packed-dynamic.mjs` into it, run `npm ci --ignore-scripts` and `npm run build --workspaces`, then run `NIGHTJAR_TEST_FAMILY=martlet PLAYWRIGHT_EXECUTABLE_PATH=/usr/bin/chromium node scripts/test-tabs-packed-dynamic.mjs`; repeat with `krigsvold`. Both fail on the focused disabled-tab assertion at that base. Omit `NIGHTJAR_TEST_FAMILY` to run both families after the fix. No test assertion was weakened.

## Scope and follow-up

The paired React components are experimental application extensions, not a source-site visual object. With the connected design MCP tools unavailable, this review used the offline Martlet grammar/source guidance at `martlettheme/npm` revision `8190e1ad71788c15bec19eac4875af7e15f4f8cf` and Krigsvold guidance at `krigsvoldtheme/npm` revision `f567b51abbe199f89cbb09b5a8cb9e77bed1e117` (React 0.1.0 / theme 2.1.0). Their shared expectation is understandable keyboard focus and recovery; their presentation stays independently owned. The search of the current portable Jekyll and Astro example sources found no corresponding ARIA tablist controller to claim as tested or silently modify. A future paired task needing tabs should establish and exercise its own appropriate native/adapter behavior in those frameworks.

The 2026-10-29 React performance baseline recorded roughly 74.4 KB compressed JavaScript for an article in a local cold-transfer measurement, after a prior 16.3% reduction. It still hydrates the shared React/runtime and family bundle; selective hydration is an architectural follow-up requiring interaction, server-rendering, focus and fallback evidence, not a claim that the bytes are unavoidable or a reason to remove the families' type or fonts. See `examples/react-catalog/PERFORMANCE.md` for method and limits.

Server-rendered interactive React controls require successful hydration for React handlers; a consumer requiring an operable no-JavaScript experience must supply an appropriate alternate path. Manual assistive-technology, Firefox/WebKit, real zoom, physical print, RTL/localization and sustained-use validation remain open. This review does not certify accessibility or cross-framework parity.
